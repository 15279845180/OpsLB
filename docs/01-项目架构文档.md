# OpsLB 项目架构文档（V2.5）

## 一、项目概述

OpsLB 是一个基于 OpenSIPS + Go 的轻量级 SIP 负载均衡系统，用于对接运营商 SIP 中继和下游 PBX/网关。

**核心职责：**
- IP 白名单认证（入局网关管理）
- 并发控制（入局 + 出局双层限制）
- 智能路由（优先级 > 权重 > CPS 筛选）
- 话单记录（按日期分表，异步批量写盘）

## 二、技术栈

| 组件 | 技术 | 版本 |
|------|------|------|
| SIP 代理 | OpenSIPS | 3.6.4 |
| 后端 API | Go + Gin | 1.21+ |
| 缓存/并发 | Redis | 6.x+ |
| 数据库 | MySQL | 8.0+ |
| 前端 | HTML + vanilla JS | - |

## 四、核心流程

### 4.1 INVITE 呼叫流程（V2.5 接口合并）

```
INVITE 到达 OpenSIPS :5060
  │
  ▼
route[INBOUND]
  check_source_address()  ← MySQL cfg_inbound_ips 白名单
  │
  ▼
route[OUTBOUND]
  async rest_post(/api/call/allocate, {call_id, caller, called, inbound_ip})
  │
  ▼
Go: handlers.Allocate()
  │
  ├─ 1. cache.GetInboundGatewayByIP(ip)      ← 内存缓存（微秒级）
  │     └─ 不在白名单 → 返回 allowed=false
  │
  ├─ 2. cache.AllocateInboundCall()          ← Redis Lua 原子
  │     ├─ FULL    → 返回 allowed=false
  │     ├─ REJECT  → 返回 allowed=false
  │     ├─ SUCCESS → 新通话，创建话单
  │     └─ DUPLICATE → 重传，复用已有结果
  │
  ├─ 3. filterAvailableGatewaysFromCache()   ← 内存缓存选路
  │     └─ 优先级从高到低遍历
  │       ├─ 检查并发（Redis counter）
  │       └─ 检查CPS（Redis 秒级限流）
  │
  ├─ 4. selectByWeightFromCache()            ← 加权轮询
  │
  ├─ 5. cache.AllocateOutboundCall()         ← Redis Lua 原子
  │     └─ 失败 → 回滚入局并发
  │
  └─ 6. cache.EnqueueCallRecord()            ← 异步写话单
  │
  ▼
返回 JSON: {allowed, gateway_id, gateway_ip, gateway_port, protocol}
  │
  ▼
route[RESUME_ALLOCATE] (异步回调)
  解析 JSON → $du = sip:xxx@gateway_ip:port
  → create_dialog("B")
  → store_dlg_value(...)
  → t_relay()
```

### 4.2 BYE/CANCEL/failure 释放流程

```
BYE/CANCEL/failure 到达
  │
  ▼
OpenSIPS: rest_post(/api/call/release, {call_id, reason, status_code})
  │
  ▼
Go: handlers.ReleaseCall()
  ├─ cache.ReleaseCall()    ← Redis 释放并发计数器
  └─ go updateCallRecordAsync() ← 异步更新话单状态
```

### 4.3 话单生命周期

```
INVITE (allocate)
  → 创建话单 (status_code=0)
  → 入异步队列 → 批量写 MySQL

ANSWER (200 OK)
  → 更新 answer_time, status_code=200

BYE/CANCEL/FAILURE (release)
  → 更新 end_time, talk_duration, status_code
```

## 五、并发控制设计

### 5.1 双层并发限制

| 层级 | Redis Key | 说明 |
|------|-----------|------|
| 入局 | `inbound:{id}:calls` | 限制每个入局网关最大并发 |
| 出局 | `gateway:{id}:calls` | 限制每个出局网关最大并发 |

### 5.2 原子操作（Lua 脚本）

所有并发申请/释放均使用 Redis Lua 脚本保证原子性：
- `AllocateInboundCall`: HSET + INCR 原子操作
- `AllocateOutboundCall`: HGET 校验 + INCR 原子操作
- `ReleaseCall`: DECR + HSET released 标记

### 5.3 超时兜底

```go

// 每60秒扫描超时5分钟未释放的通话，自动释放
```

## 七、接口设计：为什么是3个而不是1个？

### 7.1 核心矛盾：时间线不可合并

一通正常电话跨越几秒到几分钟，不同阶段需要不同的操作：

```
T=0s      INVITE 到达
              │
              ├─ /api/call/allocate   申请并发+选路，拿到出局网关地址
              │                        ← 必须拿到结果才能转发INVITE
T=0.1s    INVITE 转发到出局网关
              │
T=3s      200 OK 返回
              │
              ├─ /api/route/event     记录接通时间（answer_time）
              │                       ← 异步，不阻塞信令
T=3.1s    ACK 转发
              │
          ... 通话中（可能10秒，也可能10分钟）...
              │
T=310s    BYE 到达
              │
              ├─ /api/call/release    释放并发 + 计算通话时长
              │                       ← 必须同步，否则计数器泄漏
T=310.1s  BYE 转发
```

**结论：** allocate 和 release 之间隔了几十秒到几十分钟，物理上无法合并。

### 7.2 V2.5 合并的是什么？

合并的是 **INVITE 这一时刻内部的3次调用**。改造前 INVITE 到达后需要串行调3次 Go：

```
改造前（V2.4）INVITE 路径：
  1. async /allocate/inbound   授权入局并发
     └─ 回调 RESUME_INBOUND
  2. async /route/select       查询出局网关
     └─ 回调 OUTBOUND_ROUTE_HANDLER  
  3. async /allocate/outbound  授权出局并发
     └─ 回调 RESUME_OUTBOUND → 转发

改造后（V2.5）INVITE 路径：
  1. async /allocate           一次完成全部（入局+选路+出局）
     └─ 回调 RESUME_ALLOCATE → 转发
```

从 INVITE 角度看：3次 async → 1次 async。但从全程看：INVITE 时1次 + BYE/CANCEL时1次 release，共2次。

### 7.3 三个接口职责一览

| 接口 | 谁调用 | 同步/异步 | 作用 | 调用时机 |
|------|--------|-----------|------|---------|
| `/api/call/allocate` | route[OUTBOUND] | async | 入局鉴权+选路+出局并发申请 | INVITE 到达时 |
| `/api/call/release` | CANCEL/BYE/FAILOVER/DLG_TIMEOUT | **sync** | 释放入局+出局并发计数器 | 呼叫结束时 |
| `/api/route/event` | onreply_route/RESUME_ALLOCATE | sync或async | 更新话单状态（接通/失败） | 状态变更时 |

> **关键区别：** release 用同步调用（`rest_post`），因为若释放失败会导致并发计数器泄漏，OpenSIPS Worker 必须等它完成。event 用异步调用（`async`）或不阻塞的同步调用，因为话单更新失败了不影响通话。

### 7.4 改造前后 HTTP 调用频次对比

| 场景 | 改造前(V2.4) | 改造后(V2.5) |
|------|-------------|-------------|
| INVITE 成功 | 3次 async | 1次 async |
| INVITE 失败（无可用网关） | 1次 async | 1次 async |
| 200 OK | 0次 | 1次 async |
| BYE 释放 | 1次 sync | 1次 sync |
| **每通成功呼叫总计** | **4次** | **3次**（1 async + 1 async + 1 sync）|

> **注意：** 200 OK 的 answer 事件（V2.5新增）是 async 异步调用，不阻塞 SIP 信令。之前版本遗漏了此调用，导致话单永远不写 answer_time。

## 九、关键设计决策

1. **并发权威在 Go**：OpenSIPS 不做任何并发计数，全部委托 Go + Redis
2. **内存缓存选路**：网关配置缓存在 Go 内存中，30秒刷新，选路无需查 MySQL
3. **Lua 原子操作**：所有 Redis 写操作通过 Lua 脚本保证原子性
4. **话单异步**：批量写入 + 多消费者，避免阻塞 SIP 信令
5. **接口合并**：3次 HTTP 合并为 1次，降低 OpenSIPS Worker 阻塞风险
